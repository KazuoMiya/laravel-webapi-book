# 第1章 Web APIとは何か

Web APIは「HTTPで頼むと、JSONで答えが返ってくる窓口」です。この章では、その土台となるHTTPの仕組みと、APIの設計思想であるRESTを学びます。コードを書く前にここを押さえると、以降の章で出てくる用語がすべてつながります。

## この章のゴール

- HTTPのリクエストとレスポンスの組み立てを説明できる
- 操作に合ったメソッドと、結果に合ったステータスコードを選べる
- curlでAPIを呼び出し、応答を読める

## 1.1 クライアントとサーバー

Webの通信には必ず2つの立場があります。お願いを送る側が「クライアント」、お願いを受けて答えを返す側が「サーバー」です。ブラウザーやスマートフォンアプリはクライアントで、本書で作るLaravelのアプリはサーバーです。

クライアントからサーバーへのお願いを「リクエスト」、サーバーからの答えを「レスポンス」と呼びます。1回のリクエストに対して、通常は1つの最終的なレスポンスが返ります（通信が途中で切れた場合などを除きます）。この決まりごとを定めたものがHTTP（HyperText Transfer Protocol）です。

画面を返すWebサイトとWeb APIの違いは、レスポンスの中身だけです。WebサイトはHTML（人が見る画面）を返し、Web APIはJSON（プログラムが読むデータ）を返します。

## 1.2 リクエストとレスポンスの中身

HTTP/1.1のやり取りは、人が読める文字の並びとして表せます。HTTP/2以降は内部ではフレームという別の形式で送りますが、メソッドやヘッダーの意味は同じです。たとえば、ID 1のタスクを取得するリクエストは次のようになります。

```http
GET /api/v1/tasks/1 HTTP/1.1
Host: localhost
Accept: application/json
Authorization: Bearer 1|abcdef123456
```

1行目を「リクエストライン」と呼び、メソッド（GET）、パス（/api/v1/tasks/1）、HTTPのバージョンが並びます。2行目以降は「ヘッダー」で、リクエストの付加情報を「名前: 値」の形で書きます。データを送るときは、ヘッダーの後に空行を1つ挟んで「ボディ」を続けます。

これに対するレスポンスは次のとおりです。

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"data":{"id":1,"title":"牛乳を買う","is_done":false}}
```

1行目の「200 OK」がステータスコードで、処理の結果を3桁の数字で表します。空行の後のボディに、JSON形式のデータが入っています。

## 1.3 HTTPメソッド

メソッドは「何をしたいか」を表す動詞です。Web APIでは主に次の5つを使います。

| メソッド | 意味 | 例 | 安全 | 冪等 |
| --- | --- | --- | --- | --- |
| GET | 取得する | タスク一覧を見る | はい | はい |
| POST | 新しく作る | タスクを登録する | いいえ | いいえ |
| PUT | まるごと置き換える | タスクの全項目を更新する | いいえ | はい |
| PATCH | 一部を変更する | タスクを完了にする | いいえ | いいえ（設計次第） |
| DELETE | 削除する | タスクを消す | いいえ | はい |

「安全」とは、サーバーのデータを変えないという意味です（アクセスの記録を残すといった付随的な処理は除きます）。GETは何度呼んでもデータが変わらないので安全です。

「冪等（べきとう）」とは、同じリクエストを何回送っても結果が同じになる性質です。同じタスクを2回DELETEしても「消えている」という結果は変わりません。一方、POSTを2回送るとタスクが2つできてしまいます。通信が途切れたときに再送してよいかを判断するために、この性質は重要です。

## 1.4 ステータスコード

ステータスコードは百の位で大まかな意味が決まっています。

| 範囲 | 意味 | 代表例 |
| --- | --- | --- |
| 2xx | 成功 | 200 OK、201 Created、204 No Content |
| 3xx | 別の場所を見てほしい | 301 Moved Permanently、304 Not Modified |
| 4xx | クライアント側の誤り | 400 Bad Request、401 Unauthorized、403 Forbidden、404 Not Found、422 Unprocessable Content、429 Too Many Requests |
| 5xx | サーバー側の誤り | 500 Internal Server Error、503 Service Unavailable |

Web APIでは、ステータスコードを正しく返すことがとても大切です。クライアントはまずステータスコードを見て、成功したか、入力を直すべきか、時間をおいて再試行すべきかを判断するからです。エラーなのに200を返すAPIは、使う側を混乱させます。全コードの早見表は付録にまとめました。

> つまずきポイント：401と403の違い
>
> 401の名前は Unauthorized（認可されていない）ですが、実際の意味は「あなたが誰か分からない」、つまり認証の失敗です。ログインし直せば解決する可能性があります。403 Forbidden は、本書の設計では「あなたが誰かは分かったが、それは許可されていない」という意味で、ログインし直しても解決しません。名前に引きずられて逆に使ってしまう誤りがよくあります。

## 1.5 よく使うヘッダー

| ヘッダー | 向き | 役割 |
| --- | --- | --- |
| Content-Type | 両方 | ボディのデータ形式。JSONなら application/json |
| Accept | リクエスト | 受け取りたいデータ形式。Laravelでは application/json を付けるとエラーもJSONで返る |
| Authorization | リクエスト | 認証情報。本書では Bearer の後にトークンを付ける |
| Location | レスポンス | 新しく作ったデータのURL。201 Createdと一緒に返す |
| Retry-After | レスポンス | 再試行してよい時期。秒数か日時で示す（本書の429では秒数）。429や503と一緒に返す |

## 1.6 JSON

JSON（JavaScript Object Notation）は、データを文字で表すための形式です。人が読んでも分かりやすく、ほとんどのプログラミング言語で扱えます。

```json
{
  "id": 1,
  "title": "牛乳を買う",
  "is_done": false,
  "priority": 2,
  "due_date": "2026-11-10",
  "tags": ["買い物", "家"],
  "memo": null
}
```

波かっこ `{ }` は「オブジェクト」で、名前と値の組を並べます。名前は必ずダブルクォートで囲みます。値に使える型は、文字列、数値、真偽値（true または false）、null（値がない）、配列 `[ ]`、オブジェクトの6種類です。日付専用の型はないため、文字列で表します。

## 1.7 REST

RESTは、Web APIを分かりやすく設計するための考え方です。中心にあるのは「リソース（資源）」という考え方で、APIが扱う対象を名詞としてURLで表し、操作はHTTPメソッドで表します。

| やりたいこと | RESTらしい設計 | 避けたい設計 |
| --- | --- | --- |
| タスク一覧を取得 | GET /tasks | GET /getTasks |
| タスクを作成 | POST /tasks | POST /createTask |
| ID 5のタスクを削除 | DELETE /tasks/5 | POST /deleteTask?id=5 |

もう1つの大切な原則が「ステートレス」です。サーバーは前のリクエストの内容を覚えておかず、毎回のリクエストに必要な情報（認証トークンなど）をすべて含めます。こうすると、サーバーを何台に増やしても、どのサーバーが受けても同じ答えを返せます。

> 設計判断メモ：REST、GraphQL、gRPCのどれを選ぶか
>
> 決めたこと：本書のAPIはRESTで作る。
>
> 選ばなかった案：GraphQL は、使う側が欲しい項目を指定して1回で取得できるが、仕組みが複雑で、HTTPのキャッシュやステータスコードを生かしにくい。gRPC は、高速なバイナリー形式で通信できるが、ブラウザーから直接呼ぶには工夫が必要で、主にサーバー同士の通信に向く。
>
> 理由：HTTPの仕組み（メソッド、ステータスコード、キャッシュ）をそのまま生かせ、ブラウザー、スマートフォン、IoT機器のどれからも呼びやすい。初学者にとっても仕組みを理解しやすい。
>
> 見直す条件：画面ごとに必要な項目が大きく違い、リクエストの回数が問題になるとき（GraphQL）。社内のサービス同士で大量の通信を高速に行うとき（gRPC）。

## 1.8 curlでAPIを呼んでみる

curl（カール）は、ターミナルからHTTPリクエストを送るコマンドです。macOSやWindows 11には最初から入っています。公開されているGitHubのAPIを呼んでみましょう。

```bash
$ curl -i https://api.github.com/users/laravel
```

`-i` を付けると、ボディだけでなくステータスコードとヘッダーも表示されます。`HTTP/2 200` に続いてヘッダーが並び、空行の後にLaravelのGitHubアカウント情報がJSONで表示されるはずです。

本書ではこの後、自分で作ったAPIにもcurlでリクエストを送って動作を確かめます。主なオプションは次のとおりです。

| オプション | 意味 |
| --- | --- |
| -i | レスポンスのヘッダーも表示する |
| -X メソッド | メソッドを指定する（省略するとGET） |
| -H "名前: 値" | ヘッダーを付ける |
| -d 'データ' | ボディにデータを付ける |

## AIに頼むなら

AIは用語の説明が得意ですが、細部を誤ることがあります。説明させたら、本書の内容と照らし合わせましょう。

```text
HTTPのPUTとPATCHの違いを、タスク管理APIを例にして、初学者向けに説明してください。
冪等性にも触れてください。
```

- 1.3節の表と矛盾していないか（PATCHを常に冪等だと言い切っていないか）を確かめる
- 存在しないステータスコードやヘッダーを挙げていないかを確かめる

## まとめ

- Web APIは、HTTPのリクエストを受けてJSONのレスポンスを返す
- 何をしたいかはメソッドで、結果はステータスコードで伝える
- RESTでは、対象を名詞のURLで表し、操作をメソッドで表す
- サーバーは前のリクエストを覚えない（ステートレス）
