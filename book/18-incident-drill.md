# 第18章 障害対応ドリル

本番で障害が起きたときに落ち着いて対応できるかどうかは、経験の量で大きく変わります。とはいえ、本物の障害を待つわけにはいきません。この章では、TaskBoard APIで起こりがちな6つの障害を、症状から原因へとたどる練習をします。研修では、講師が症状だけを伝え、受講者が調べ方を考える形で進めると効果的です。

## この章のゴール

- 症状から調べる順番を組み立て、ログとリクエストIDで原因を絞り込める
- すぐ元に戻すか、直して進めるかを判断できる
- 誰かを責めずに仕組みを直すための「ふりかえり」を書ける

## 18.1 障害対応の基本の流れ

1. 検知する（監視のアラート、利用者からの連絡）
2. 影響を把握する（誰が、どの機能で、どれくらい困っているか）
3. 応急処置をする（まず被害を止める。切り戻し、機能の一時停止など）
4. 原因を調べる
5. 恒久的な対策をする
6. ふりかえる

大切なのは、原因が分かる前でも被害を止めることを優先する点です。そして、対応中に行ったことを時刻とともに記録しておきます。この記録が、最後のふりかえりの材料になります。

> 設計判断メモ：まず切り戻す
>
> 決めたこと：直前のデプロイが原因と疑われるときは、原因の特定より先に、前のバージョンに切り戻す。
>
> 選ばなかった案：その場で修正して、新しいバージョンをデプロイする（ロールフォワード）。原因が明らかで修正が小さければ速いこともあるが、焦りの中での修正は新しい誤りを生みやすい。
>
> 理由：切り戻しは手順が決まっていて、速く確実に被害を止められる。原因の調査は、落ち着いてからでもできる。
>
> 見直す条件：マイグレーションで既存のデータを変えた後など、切り戻すとかえって壊れる場合。第17章の段階的なマイグレーションは、いつでも切り戻せるようにするための工夫でもある。

## 18.2 シナリオ1：デプロイ直後に500が急増

症状：新しいバージョンをデプロイした数分後から、5xxエラーの割合が急上昇した。利用者から「タスクを保存できない」という連絡が届いている。

調べ方：まず監視のグラフで、エラーが増え始めた時刻とデプロイの時刻が一致するかを確かめます。一致すれば、18.1節の判断に従って切り戻してから、ログを調べます。レベルが error のログを探すと、次のような記録が見つかります。

```json
{"message":"Mail::raw(): Argument #1 must be of type string, null given","level_name":"ERROR","context":{"request_id":"7f3c9a2e-..."},"datetime":"2026-11-20T01:12:03+00:00"}
```

request\_id で同じリクエストのログを集めると、新しく追加したメール通知の処理で、本来文字列が入るはずの値が null になっていたと分かります。その値は `config('mail.footer')` で読んでおり、config/mail.php では環境変数 MAIL\_FOOTER を参照していました。

原因：開発者は MAIL\_FOOTER を、自分の .env と .env.example には追加しましたが、本番のコンテナーに渡す環境変数には追加し忘れていました。本番では .env ファイルを使わず、環境変数だけで設定を渡しているので（17.10節）、値が null になりました。開発環境では .env に値があったため、誤りに気づきませんでした。

対処：切り戻した後、本番の環境変数に MAIL\_FOOTER を追加し、改めてデプロイします。

再発防止：必要な環境変数がないときは、コンテナーの起動そのものを失敗させます。17.10節の entrypoint.sh の確認の一覧に MAIL\_FOOTER を加えます。起動に失敗すれば、新しいコンテナーは利用者のリクエストを受ける前に止まり、古いバージョンが動き続けます。あわせて、デプロイの手順に「.env.example に増えた項目が、本番の環境変数にもあるかを確かめる」を加えます。

```sh
# docker/entrypoint.sh の確認の一覧に追加する
for name in APP_KEY DB_HOST DB_DATABASE DB_USERNAME DB_PASSWORD REDIS_HOST MAIL_FOOTER; do
```

## 18.3 シナリオ2：一覧APIが急に遅い

症状：チームのタスク一覧（GET /api/v1/teams/{team}/tasks）の応答時間が、あるチームだけ数秒かかるようになった。そのチームは最近メンバーとタスクが急に増えた。

調べ方：まず第17章の遅いSQLのログを見ましたが、何も記録されていませんでした。1つ1つのSQLは速いからです。そこで、同じ条件（多数のタスクと担当者）を開発環境で再現し、1回のリクエストで実行されたSQLを数えると、ほとんど同じSQLが数十回実行されていました。

```text
select * from `users` where `users`.`id` = ? limit 1
select * from `users` where `users`.`id` = ? limit 1
select * from `users` where `users`.`id` = ? limit 1
...
```

原因：最近の変更で一覧の応答に担当者の名前を加えたとき、`with('assignee')` を書き忘れていました（N+1問題）。開発環境では第7章の設定でエラーになるはずでしたが、この変更にはテストがなく、開発中に一覧を呼ばなかったため見逃されました。本番ではエラーにしない設定なので、遅くなるだけで動き続けていました。

対処：`with(['tags', 'assignee'])` に直してデプロイします。

再発防止：一覧のAPIには必ずテストを書きます。テストは本番以外の環境で動くので、N+1問題があればエラーとして検出されます。さらに、問い合わせの回数に上限を設けるテストも有効です。

```php
use Illuminate\Support\Facades\DB;

DB::enableQueryLog();

$this->getJson("/api/v1/teams/{$team->id}/tasks")->assertOk();

// タスクの件数が増えても、問い合わせの回数が増えないことを確かめる
$this->assertLessThan(10, count(DB::getQueryLog()));
```

本番でも気づけるように、1回のリクエストでのSQLの合計時間が長いときに記録する設定も加えておきます。1つ1つは速いSQLでも、数が多ければ合計で見つけられます。

```php
// AppServiceProvider の boot()
use Illuminate\Database\Connection;
use Illuminate\Database\Events\QueryExecuted;

DB::whenQueryingForLongerThan(500, function (Connection $connection, QueryExecuted $event) {
    Log::warning('1回のリクエストで、SQLの合計時間が500ミリ秒を超えました', ['last_sql' => $event->sql]);
});
```

## 18.4 シナリオ3：429が急増

症状：429 Too Many Requests の件数が急に増えた。同時に、利用者から「ログインできない」という連絡が何件か届いた。

調べ方：数を見るだけでなく、分布を見るのがポイントです。アクセスログを、送信元のIPアドレスとアプリのバージョン（User-Agent）ごとに集計します。どのアカウントが狙われているかを知るには、ログインの失敗だけを記録する専用のログを用意しておきます。第17章の方針どおりメールアドレスそのものは記録せず、ハッシュ化した値でアカウントを区別します。

| 見えた分布 | 考えられる原因 | 対処 |
| --- | --- | --- |
| 少数のIPアドレスから、多数のメールアドレスでログインを試している | パスワードの総当たり攻撃 | 回数制限が効いていることを確認し、該当するIPアドレスを前段で遮断する |
| 多数のIPアドレスから、新しいバージョンのアプリだけが同じAPIを短い間隔で呼んでいる | アプリの不具合で、失敗するとすぐに再試行を繰り返している | アプリを修正し、Retry-After に従って間隔を空けて再試行するようにする |

原因が攻撃なら、回数制限は設計どおりに働いています。正しい利用者が巻き込まれていないかを確かめ、必要に応じて制限の単位を見直します（第12章の設計判断メモ）。

## 18.5 シナリオ4：トークン漏えいの報告

症状：利用者から「自分のAPIトークンを、誤って公開リポジトリに載せてしまった」と連絡があった。

対処：まず、そのトークンを失効させます。どのトークンか分からなければ、その利用者のすべてのトークンを失効させます。

```php
// sail tinker（本番では管理用の手順に沿って実行する）
$user = User::where('email', 'taro@example.com')->first();
$user->tokens()->delete();   // すべてのトークンを失効させる
```

次に、影響の範囲を調べます。第17章の監査ログで、漏えいした時刻以降にそのトークン（token\_id）から行われた操作を確認し、利用者に伝えます。監査ログは書き込みの操作だけを記録しているので、そのトークンで何を見られたかまでは分かりません。この限界も含めて伝えます。

もし漏えいがデータベース全体に及んだ場合でも、Sanctumはトークンをハッシュ化して保存しているので、データベースの値からトークンを復元することはできません。それでも念のため、全員のトークンを失効させて、ログインし直してもらうのが安全です。

再発防止：トークンの有効期限を見直す、利用者向けにトークンの取り扱いの注意を案内する、GitHubなどのシークレットスキャン（秘密情報の公開を検出する機能）に対応したトークンの形式を検討する、などがあります。

## 18.6 シナリオ5：Redisが停止

症状：ほぼすべてのAPIが500を返し始めた。ところが、死活監視の /up は200を返し続けている。

調べ方：エラーログに、Redisへの接続に失敗したことを示す記録が大量に出ています。TaskBoardでは、Redisを次の用途に使っていました。

| 用途 | Redisが止まると |
| --- | --- |
| 回数制限の記録（第12章） | throttle を付けたすべてのAPIがエラーになる |
| キャッシュ（第17章） | タグの一覧などがエラーになる |
| キュー（第17章） | ジョブを登録できず、登録する処理がエラーになる |
| 冪等キーのロック（第16章） | ヘッダー付きのPOSTがエラーになる |

回数制限はほぼすべてのAPIに付いているので、Redisが止まるとAPI全体が止まります。一方、/up はアプリが起動しているかしか確かめていないので、異常に気づけませんでした。

対処：Redisを復旧します。クラウドのマネージドサービスなら、待機系への切り替えが行われているかを確認します。

再発防止：/up で、データベースとRedisにも接続できるかを確かめるようにします。/up が呼ばれると DiagnosingHealth というイベントが発生するので、そこで確認し、失敗すれば /up がエラーを返すようにできます。AppServiceProvider の `boot()` に追加します。

```php
use Illuminate\Foundation\Events\DiagnosingHealth;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Event;
use Illuminate\Support\Facades\Redis;

Event::listen(function (DiagnosingHealth $event) {
    DB::select('select 1');          // データベースに接続できるか
    Redis::connection()->ping();     // Redisに接続できるか
});
```

あわせて、Redisを複数台で構成する、キャッシュの読み込みに失敗したらデータベースから直接読むようにするなど、1つの部品が止まってもサービス全体が止まらない設計を検討します。

## 18.7 シナリオ6：マイグレーションの失敗

症状：デプロイの途中、マイグレーションの段階でエラーになり、デプロイが止まった。

調べ方：エラーのメッセージには、unique インデックスを作ろうとしたところ、既存のデータに重複があった（Duplicate entry）と書かれています。`php artisan migrate:status` で、どこまで実行されたかを確かめます。

原因：開発環境のデータには重複がなかったため、テストでは問題が出ませんでした。本番には、長く運用する中でできた重複データがありました。また、MySQLではテーブルの構造を変える操作はトランザクションで取り消せないため、1つのマイグレーションの中で途中まで変更された状態が残ることがあります。

対処：デプロイの手順どおり、コンテナーの入れ替えはまだ行われていないので、古いバージョンのアプリが動き続けています。まず利用者への影響がないことを確かめます。次に、途中まで変更されたテーブルの状態を確認して元に戻し、重複データを整理してから、改めてマイグレーションを実行します。

再発防止：

- 本番に近いデータを持つ検証環境で、事前にマイグレーションを試す
- 制約を加える前に、違反するデータがないかを確かめる手順を入れる
- 1つのマイグレーションで行う変更を小さくし、失敗したときの影響範囲を狭める

## 18.8 ふりかえりを書く

障害が落ち着いたら、ふりかえりの文書を書きます。目的は、同じ障害を二度と起こさないように仕組みを直すことです。誰かの失敗を責めるためではありません。「人が間違えた」で終わらせず、「なぜ間違えられる仕組みだったのか」まで掘り下げます。

シナリオ1を例にすると、次のようになります。

- なぜ500が出たか：メールの設定値が null だったから
- なぜ null だったか：本番の環境変数に MAIL\_FOOTER がなかったから
- なぜ開発で気づかなかったか：開発環境では .env に値があったから
- なぜ仕組みで防げなかったか：必要な環境変数がそろっているかを、起動時やデプロイ時に確かめる仕組みがなかったから

最後の「なぜ」に対する答えが、再発防止策になります。ふりかえりは、次のひな形に沿って書きます。

```markdown
# 障害のふりかえり：（タイトル）

## 概要
何が起きたかを2〜3文で。

## 影響
- 期間：（開始時刻）〜（終了時刻）
- 影響を受けた利用者と機能：
- 失われたデータ：（なければ「なし」）

## 時系列
| 時刻 | 出来事 |
| --- | --- |
| 10:02 | デプロイ完了 |
| 10:07 | 5xxエラーのアラート |

## 原因
直接の原因と、それを防げなかった仕組みの原因。

## 対応
応急処置と恒久対策。

## うまくいったこと
## うまくいかなかったこと

## 再発防止策
| 対策 | 担当 | 期限 |
| --- | --- | --- |
```

## AIに頼むなら

大量のログから原因の候補を挙げてもらうのは、AIの得意な作業です。

```text
次のログは、障害が起きた時間帯のエラーログの抜粋です（個人情報とトークンは伏せてあります）。
考えられる原因の仮説を可能性の高い順に3つ挙げ、それぞれを確かめるために
次に見るべきログやデータを示してください。
（ログを貼り付ける）
```

受け取った結果では、次の点に注意します。

- AIの仮説は「確かめるべき候補」であり、結論ではない。必ずログやデータで裏付けてから対処する
- ログを渡す前に、メールアドレス、トークン、パスワードなどが含まれていないかを確かめ、伏せる

## まとめ

- 障害対応は、検知、影響の把握、応急処置、原因の調査、恒久対策、ふりかえりの順に進める
- 原因が分からなくても、直前のデプロイが疑わしければまず切り戻す
- 数だけでなく分布を見て、攻撃と不具合を見分ける
- 死活監視は、依存するサービスまで確かめる
- ふりかえりでは人ではなく仕組みに原因を求め、再発防止策に担当と期限を付ける

## 演習

1. 基礎：シナリオ3で、攻撃かアプリの不具合かを見分けるために、アクセスログで見るべき項目を3つ挙げてください。
2. 応用：6つのシナリオから1つを選び、18.8節のひな形に沿ってふりかえりの文書を書いてください。時刻や影響の人数は、想定で決めてかまいません。

解答例は付録Eにあります。

## レビュー観点

- [ ] 切り戻しの手順が文書になっていて、誰でも実行できる
- [ ] /up が、データベースやRedisなど依存するサービスも確かめている
- [ ] エラー率、応答時間、429の数、キューの長さを監視している
- [ ] すべてのログにリクエストIDが入っている
- [ ] トークンを一括で失効させる手順がある
