# 第5章 Web APIを設計する

コードを書く前に、APIの外から見える形（URL、メソッド、JSON、ステータスコード）を決めます。APIは一度公開すると、使う側のアプリが増えるほど変更しにくくなります。だからこそ、最初の設計が大切です。

## この章のゴール

- 要件から、リソースとURLを設計できる
- 成功と失敗のステータスコードを、理由とともに決められる
- JSONの形とエラーの形を、API全体でそろえられる

## 5.1 要件を整理する

まず、TaskBoard APIで「誰が何をできるか」を言葉で書き出します。

- 利用者は、メールアドレスとパスワードで登録し、ログインできる
- ログインした利用者は、自分のタスクを作成、閲覧、更新、削除できる
- 他人のタスクは、見ることも変更することもできない
- タスクには、タイトル、メモ、期限、優先度（低・中・高）、完了状態、タグを付けられる
- タスク一覧は、完了状態、優先度、タグ、キーワード、期限で絞り込める
- タスク一覧は、期限や作成日時で並べ替えられ、ページに分けて受け取れる

## 5.2 リソースを洗い出す

要件に出てくる名詞のうち、APIで扱う対象がリソースです。

| リソース | 内容 | 関係 |
| --- | --- | --- |
| ユーザー（users） | 利用者 | 1人のユーザーが多数のタスクとタグを持つ |
| タスク（tasks） | やること | 1つのタスクは1人のユーザーに属し、複数のタグを持てる |
| タグ（tags） | タスクの分類ラベル | 1つのタグは複数のタスクに付けられる。タグもユーザーごと |

タスクとタグのように「多対多」の関係は、第7章で中間テーブルを使って表します。

## 5.3 URL設計のルール

本書では次のルールでURLを決めます。

- リソースは名詞の複数形で表す（/tasks）
- 1件を指すときはIDを続ける（/tasks/5）
- 小文字を使い、単語の区切りはハイフンにする（/task-lists のように）
- 操作の種類はURLに入れず、メソッドで表す（/tasks/5/delete とはしない）
- 階層は浅く保つ。深くても「親/ID/子」の2段まで
- 先頭にバージョンを入れる（/api/v1/...）

例外は、ログインやログアウトのように「リソースの作成や削除」と捉えにくい操作です。本書では分かりやすさを優先し、/login と /logout という動詞のURLを使います。トークンというリソースを作ると捉えて POST /tokens とする設計もあり、どちらも広く使われています。

> つまずきポイント：「完了にする」をURLにしたくなる
>
> タスクを完了にする操作を、POST /tasks/5/complete のように動詞のURLで作りたくなることがあります。しかし「完了にする」は、タスクの is\_done という項目を変える更新です。PATCH /tasks/5 に {"is\_done": true} を送れば表現できます。迷ったら「どのリソースの、どの項目を変える操作か」と言い換えてみましょう。項目の変更では表せない複雑な操作に限って、動詞のURLを検討します。

## 5.4 メソッドとステータスコードを決める

タスクに関するAPIの、成功時と主な失敗時のステータスコードを決めます。

| 操作 | メソッドとURL | 成功時 | 主な失敗時 |
| --- | --- | --- | --- |
| 一覧 | GET /tasks | 200 | 401、422（絞り込み条件の誤り） |
| 作成 | POST /tasks | 201（Locationヘッダー付き） | 401、422 |
| 詳細 | GET /tasks/{id} | 200 | 401、404 |
| 部分更新 | PATCH /tasks/{id} | 200 | 401、404、422 |
| 削除 | DELETE /tasks/{id} | 204 | 401、404 |

どのAPIでも共通する失敗として、回数制限を超えたときの429と、サーバー内部の問題による500があります。

他人のタスクを指定されたとき、403（権限がない）と404（存在しない）のどちらを返すかは設計判断です。403を返すと「そのIDのタスクは存在する」ことが相手に伝わってしまいます。本書では、他人のタスクは「自分からは見えない＝存在しない」とみなして404を返します。

> 設計判断メモ：他人のタスクには404を返す
>
> 決めたこと：他人のタスクのIDを指定されたら、403ではなく404を返す。
>
> 選ばなかった案：403 Forbidden を返す。権限がないことは正確に伝わるが、「そのIDのタスクは存在する」ことも伝わってしまう。
>
> 理由：利用者にとって他人のタスクは見えないものであり、存在を知らせる必要がない。IDを順に試して、件数や存在を探られる手がかりも減らせる。
>
> 見直す条件：管理者が他のユーザーのタスクを閲覧する機能を作るとき。また、チームのように「存在は見えているが操作は許されない」場面では403を使う（第11章）。

PUTとPATCHの違いにも触れておきます。PUTは全項目を送って置き換え、PATCHは変えたい項目だけを送ります。タスクの完了だけを切り替えたい場面が多いので、本書ではPATCHを使います。

> 設計判断メモ：IDは連番のままにする
>
> 決めたこと：タスクやユーザーのIDは、1、2、3と増える連番の整数にする。
>
> 選ばなかった案：UUIDやULIDのような、推測されにくい長い文字列のIDにする。LaravelではモデルにHasUuidsやHasUlidsを付けるだけで使える。
>
> 理由：他人のデータは認可で守っているので、IDを推測されても中身は見えない。連番は短くて扱いやすく、学習の題材としても分かりやすい。
>
> 見直す条件：件数や増え方（たとえば利用者の数）を外部に知られたくないとき。また、招待のように「IDを知っていること」自体が権限になるものには、連番を使わない（第11章）。

## 5.5 JSONの形を決める

レスポンスのJSONは、次のルールでそろえます。

- キー名は小文字とアンダースコア（スネークケース）にする（due\_date、is\_done）
- 本体は data というキーの中に入れる。一覧のページ情報などは meta と links に入れる
- 日時はISO 8601形式の文字列で、タイムゾーン付きで返す（2026-11-03T09:00:00+00:00）
- 日付だけの値は YYYY-MM-DD の文字列にする
- 真偽値は true または false、値がないときは null を返す（キーを省略しない）

タスク1件のレスポンスは次の形にします。

```json
{
  "data": {
    "id": 12,
    "title": "牛乳を買う",
    "memo": "低脂肪のもの",
    "due_date": "2026-11-10",
    "priority": "high",
    "is_done": false,
    "tags": [
      { "id": 3, "name": "買い物" }
    ],
    "created_at": "2026-11-03T09:00:00+00:00",
    "updated_at": "2026-11-03T09:00:00+00:00"
  }
}
```

優先度はデータベースでは1から3の数値で保存しますが、APIでは low、medium、high という文字列で返します。数値より意味が分かりやすく、将来データベースの持ち方を変えてもAPIの形を保てるからです。データベースの形をそのままAPIに出さないことは、API設計の大切な考え方です。

本体を data に入れる理由は、後からページ情報などを追加しても形が崩れないためです。

## 5.6 一覧の絞り込み、並べ替え、ページング

タスクが数千件あっても、一度に全部を返すわけにはいきません。一覧APIは、クエリ文字列で条件を受け取ります。

| パラメーター | 例 | 意味 |
| --- | --- | --- |
| is\_done | is\_done=false | 完了状態で絞り込む |
| priority | priority=high | 優先度で絞り込む |
| tag | tag=買い物 | タグ名で絞り込む |
| q | q=牛乳 | タイトルとメモのキーワード検索 |
| due\_before | due\_before=2026-11-30 | 指定日までに期限が来るもの |
| sort | sort=-due\_date | 並べ替え。先頭の - は降順。due\_date、priority、created\_at から選ぶ |
| page | page=2 | ページ番号（1から） |
| per\_page | per\_page=20 | 1ページの件数（1〜100、省略時は15） |

レスポンスにはページ情報を付けます。

```json
{
  "data": [ { "id": 12, "title": "牛乳を買う" } ],
  "links": {
    "first": "http://localhost/api/v1/tasks?page=1",
    "last": "http://localhost/api/v1/tasks?page=4",
    "prev": null,
    "next": "http://localhost/api/v1/tasks?page=2"
  },
  "meta": {
    "current_page": 1,
    "last_page": 4,
    "per_page": 15,
    "total": 52
  }
}
```

件数の上限（100件）を決めておくのは、per\_page=100000 のような要求でサーバーが重くなるのを防ぐためです。

## 5.7 エラーの形をそろえる

エラーのときも、必ずJSONで返し、形をそろえます。使う側が、どのエラーでも同じ書き方で処理できるようにするためです。本書では、Laravelの標準に合わせた次の形にします。

```json
{
  "message": "タスクが見つかりません。"
}
```

入力の誤り（422）のときだけ、項目ごとの誤りを errors に入れます。

```json
{
  "message": "タイトルは必須です。 (and 1 more error)",
  "errors": {
    "title": ["タイトルは必須です。"],
    "due_date": ["期限は日付で指定してください。"]
  }
}
```

エラーの形には、RFC 9457（Problem Details）という標準規格もあります。type、title、status、detail というキーを持ち、Content-Type に application/problem+json を使う形式です。複数の組織が使う公開APIでは検討する価値があります。本書では、Laravelの標準と同じ形にして実装を簡単にします。

## 5.8 バージョニング

APIを使うアプリは、APIの変更に合わせてすぐには更新できません。特にスマートフォンアプリは、利用者が更新するまで古い版が使われ続けます。そこで、互換性のない変更をするときはURLのバージョンを上げ、古い版もしばらく残します。

| 変更の例 | 互換性 | バージョン |
| --- | --- | --- |
| レスポンスに新しいキーを追加する | 保たれる | そのまま |
| 任意の入力項目を追加する | 保たれる | そのまま |
| キー名を変える、キーを削除する | 壊れる | 上げる（v2） |
| 必須の入力項目を追加する | 壊れる | 上げる（v2） |
| 値の意味や型を変える | 壊れる | 上げる（v2） |

使う側も「知らないキーが増えても無視する」ように作っておくと、APIを安全に育てられます。

## 5.9 完成した設計

ここまでの決定をまとめると、TaskBoard API v1は次のとおりです。

| メソッド | URL | 入力 | 成功時の応答 |
| --- | --- | --- | --- |
| POST | /api/v1/register | name、email、password、password\_confirmation | 201 ユーザーとトークン |
| POST | /api/v1/login | email、password、device\_name | 200 ユーザーとトークン |
| POST | /api/v1/logout | なし | 204 |
| GET | /api/v1/me | なし | 200 ユーザー |
| GET | /api/v1/tasks | 5.6のクエリ | 200 タスクの一覧とページ情報 |
| POST | /api/v1/tasks | title（必須）、memo、due\_date、priority、is\_done、tags | 201 タスク |
| GET | /api/v1/tasks/{id} | なし | 200 タスク |
| PATCH | /api/v1/tasks/{id} | 変更したい項目だけ | 200 タスク |
| DELETE | /api/v1/tasks/{id} | なし | 204 |
| GET | /api/v1/tags | なし | 200 タグの一覧 |

タグは専用の作成APIを持たず、タスクの作成や更新時に tags に名前の配列を渡すと、なければ自動で作られる仕様にします。使う側の手間を減らすための判断です。

## AIに頼むなら

設計案の批評は、AIに頼みやすい作業です。ただし、本書の設計ルールを一緒に渡さないと、一般論の答えが返ってきます。

```text
タスク管理APIに、タスクへのコメント機能を加えたいと考えています。
次の設計ルール（5.3節）に従って、URL、メソッド、成功時と失敗時のステータスコードを提案してください。
ルールに反する案を出す場合は、その理由も示してください。
（設計ルールを貼り付ける）
```

- 提案が設計ルールを守っているかを確かめる
- 他人のデータに404を返す方針など、本書の判断が反映されているかを確かめる

## まとめ

- 名詞のURLとメソッドの組み合わせで操作を表す
- 成功と失敗をステータスコードで正しく伝え、他人のデータには404を返す
- JSONの形、日付の書き方、エラーの形をAPI全体でそろえる
- 互換性を壊す変更はバージョンを上げる

## 演習

1. 基礎：「タスクを複製する」操作を加えるとしたら、メソッド、URL、成功時のステータスコードをどうしますか。理由とともに答えてください。
2. 応用：タスクに「コメント」を付ける機能を設計してください。1つのタスクに複数のコメントを付けられ、コメントを編集、削除できるのは書いた本人だけです。URL、リクエストとレスポンスのJSON、ステータスコードを決めてください。

解答例は付録Eにあります。

## レビュー観点

- [ ] URLは名詞の複数形で、階層が浅い
- [ ] 他人のデータへの応答（404）が決まっている
- [ ] エラーの形が、すべてのAPIでそろっている
- [ ] 既存のAPIの互換性を壊す変更をしていない
